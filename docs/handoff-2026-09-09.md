## The positioning — settled, do not drift back

Jennifer rewrote this several times. The final read is specific, and earlier
drafts got it wrong in ways that are easy to fall back into.

**Tagline: _"The platform for forward-deployed operators"_** — in the hero
kicker and as the share-card `<meta name="description">`.

Rejected: *"the platform for forward-deployed talent who are not engineers"*.
"Talent" is recruiter-speak and reads badly when the members ARE the audience,
and defining people by what they are not is weak.

**The premise is job + AI, not career change.** Almost nobody here has left
their job. The CMO is still the CMO who also prototypes the product. The
retention lead still owns retention *and* builds the flows she used to brief
out. The CFO still signs off the accounts *and* runs finance from a terminal.

> Never write "Formerly X", never use past tense about the existing role. The
> previous career is the **asset**, not the affliction. An early draft had a
> title generator producing "Recovering Lawyer" — exactly backwards.

**The villain is the org chart, not the person.** Companies noticed AI and drew
one new box, Head of AI, then stopped. That box does nothing for the CMO who
codes. The reader isn't confused; the structure is out of date.

**The tone is confident.** The site's NAME is the only self-deprecating thing
about it. Everything underneath is a page of people who are obviously good at
things. Cut anything that reads as bleak, existential or defeated — an earlier
version rotated the headline verb through "owe", "cost" and "am", which turned
a wry line into an identity crisis. The headline does not rotate at all now:
people know perfectly well what they build, it is the *title* that stopped
describing them.

**The homepage is deliberately bare** — headline, paragraph, two buttons,
directory. Jennifer explicitly deleted a drifting-words canvas, a scrolling
ticker, a stat row, a job-title generator and two whole argument sections.
Do not reintroduce them. The test suite asserts they are absent.

## How it works

```
app/
  main.py       routes, validation, spam defence
  db.py         SQLAlchemy models; SQLite locally, Postgres in production
  taxonomy.py   THE VOCABULARY. Job titles, what people add on top, tools,
                availability, the plurality score. Edit this first —
                everything else derives from it
  mailer.py     Resend relay, falls back to console logging
  templates/    Jinja2
  static/       one stylesheet. There is no JavaScript any more
seed.py         six invented example profiles for local dev only
```

### Decisions worth knowing

**Nobody's email is ever rendered.** `contact_email` is read only by the mailer.
The contact form posts to the server, which forwards the message with the
sender's address as reply-to. Scrapers get nothing. This is a feature — say so.

**No accounts, no passwords.** Each profile gets a random `edit_token`, emailed
once and shown once. Losing it means losing edit access; the page says so.

**Deletes are soft.** "Take me off the site" sets `visible = False`, so a
mis-click is recoverable from the database.

**The plurality score is derived, never entered** — the count of things someone
ticked beyond their job title, capped at 10.

**`former_life` is a misleading column name.** It holds the person's CURRENT job
title. It was named during the career-change draft and kept because
`create_all()` does not alter existing tables, so renaming it would need a
migration against a live database. All user-facing labels say "job title".

**Filtering happens in Python**, not SQL, because the list fields are JSON
columns. Fine for hundreds of profiles; past a few thousand, move `former_life`
to a SQL filter and add a join table for the rest.

**Spam defence is light** — a honeypot field plus an in-memory per-IP rate
limit. In-memory means it resets on redeploy and doesn't span instances. Move
it to the database if the site gets attention.

## Traps that cost real time

**`gh` flips accounts on its own.** It switched from `thebluntamerican` back to
`jenvalidify` twice mid-session, and `gh repo edit` then 404s with "Could not
resolve to a Repository". Check `gh api user --jq .login` immediately before
any push. `.git/hooks/pre-push` guards against it.

**The Railway CLI on this Mac is Laura Wynch (laura@validify.co.uk).**
`~/.railway/config.json` holds one token plus the directory→project links for
the Validify repos, so `railway logout` would log out every terminal and only
Laura could log back in. **Use the Railway dashboard** for anything on this
project.

**GoDaddy auto-published a "coming soon" site onto the apex.** It served a real
page with a valid GoDaddy cert and auto-titled itself from the domain, so it
looked like the real site. Clicking Unpublish three times changed nothing —
the thing doing the serving was an `A @ WebsiteBuilder Site` DNS record.
Setting **Forwarding** replaced that record and fixed it. Full detail in the
`godaddy-websitebuilder-squats-apex` memory.

**GoDaddy cannot CNAME an apex** and has no ALIAS/flattening, so: `www` gets the
CNAME to Railway, the root gets Forwarding → `https://www....` (Permanent 301,
never masking). Same pattern as attent10n.ai.

**Starlette 1.6 stopped deriving HEAD from GET**, so every route answered 405 to
a HEAD request — what most uptime monitors send first. Fixed by mirroring GET
onto HEAD across `app.routes` at the end of `main.py`. **Worth checking on
ATTENT10N** if it runs the same Starlette version.

**`curl -X HEAD` exits non-zero on a bodyless reply**, so
`$(curl … || echo 000)` yields "200000" and a polling loop never matches. Use
`curl --head` with no `||` fallback.

## Running it locally

```bash
cd ~/Developer/ihavenoideawhatidoanymore
uv venv --python 3.12
uv pip install -r requirements.txt
.venv/bin/python seed.py                 # optional example profiles
.venv/bin/uvicorn app.main:app --reload
```

No environment variables needed — it falls back to a local SQLite file and
prints emails to the console instead of sending them.
